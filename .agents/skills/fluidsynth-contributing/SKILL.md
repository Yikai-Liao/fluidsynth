# 向 FluidSynth 贡献

本 skill 服务于 Yikai-Liao 的 fork 工作流，不是上游新增规章。偏好依据、全部 PR 索引和适用边界见 [references/history.md](references/history.md)。选题前读取 fork `todo` 分支的当前 README；其暂缓决定优先于这里的默认排序。本文中的 `todo` 是独立根历史的记录分支，不能合入代码 PR。

## 选什么，不选什么

- 默认先处理实际音色、力度、漏发音和踏板延音。结合触发条件、后果、可复现证据与审核成本判断；不按审计分数、一行改动或 PR 数量排序。
- 优先已有真实 MIDI／常用 SoundFont 证据的小型独立修复。人工构造可证明 bug，但不能证明常见；非默认模式、宿主动作与非法输入在问题描述中就交代。
- 多个问题即使都与 CC66 或 DLS 有关，也不自动合包。一个 PR 解决一个可独立解释和验证的问题；确有依赖时说明并考虑 stacked PR。
- 新功能先讨论；行为变更先说明真实问题与理由。较大重构先有可靠测试基础、具体问题和推进计划，不提交罗列大量缺陷却没有最小复现的大 issue。
- derselbst 在 DLS 讨论中把约 500 行 changed code 视为易消化规模的上沿，不是可用满的预算，也不是整个项目的硬限制。小而完整优于人为拆散同一修复。
- 保留已有暂缓决定：播放器控制／跨轨排序／heap merge／F35、DLS 大重构、Windows CI 整理先不推进；Android 等用户有空 review。sinc／DSP 插值先核对维护者在做的工作，不重复投稿。
- 对内存安全候选按入口单独评价；未公开漏洞按最新 SECURITY.md 私下报告，不把审计发现自动公开为 CVE 或宣称可 RCE。

## 怎么改，怎样验证

- 基于最新上游 master，不基于 release 或陈旧 fork master。先查 open PR、相关 issue 和已合并修复；#1878 的教训是不要为已被更完整方案解决的问题重提 PR。
- 先复用现有机制、宏、loader callbacks、RAII 与测试设施。把必要不变量放在掌握信息的边界验证；不能用保持代码形式不变来牺牲正确性。断言检查实际参与后续操作的对象：例如指针先偏移，再检查对齐，不只验证原地址，也不保留等价的重复断言（#1910）。
- 不夹带无关命名、注释、查询 API、生命周期或线程协议整理。也不把“最小”理解为禁止 C++ 或内部接口变更：#1902 接受了聚焦的 C++ 迁移，并把迁移与 atomic 逻辑分成两个可审查提交。
- 不破坏 include/ 下公开 API、ABI 或既有行为契约。行为修复须明确旧行为的问题和兼容性影响；内部接口可以按实际需要调整。
- 沿用上游风格：Allman braces、每个分支有花括号、空格、优先 signed integer。函数／变量用 lower_case_with_underscores，生产函数沿用 fluid_<component>_<purpose>() 与邻近代码的 LOCAL 等约定；宏名 UPPER_CASE。已有名称不为统一样式而顺手重命名，也不为小修新增转发 helper。
- 注释沿用邻近已接受代码的表达，只补理解本次改动确需的非显然原因或约束；清楚的原注释保留，不借小修润色周边文字。按用户明确偏好，不写为假想质疑辩护、罗列未发生风险或宣称安全／兼容的防御性说明。测试注释直接描述场景与预期，不写抽象保证句。新增函数须有简短用途说明；公开 API 按现有 Doxygen 顺序说明用途、参数和返回值，deprecated／since 最后；不因本次小修给未改函数补整套注释。
- 复用仓库已有 FLUID_* 宏、loader callbacks、RAII、test.h 断言、测试文件、CMake 测试注册、check／check_rendering 和 CI 配置。仅在职责确实独立或既有设施无法承接时新增文件／helper／构建机制；不自制同功能框架、不添无关依赖、不为小收益引入编译器专属实现。格式调整限于改动范围，不整库 format。
- 回归优先放在职责合适的现有测试文件，保持邻近命名和断言风格；新文件须有独立职责。保留能抓住旧 bug 的最小测试，不提交基准框架、实验日志或大规模防御性脚手架。
- 做修复前失败／修复后通过对照，并保护相邻有效行为。按真实调用路径检查同类入口，例如 CC120/CC123、单／全通道、global-controller 逐通道旧值、踏板边沿与同周期重弹；不无限枚举无关组合。
- 数值代码覆盖受影响的 float/double、GCC/Clang 与精度假设；需要时关注 x87、mingw32。本机 x86-64 成功不能替代目标平台 CI。先构建 check 依赖再用 ctest；手动渲染另跑 check_rendering。
- 所有 CI／测试应通过；失败逐项判因并如实报告。音频 bug 修复可能有预期 PCM 差异，须解释而不是强求 bit-identical。合并、发布、CI 全绿和 fork 已修是不同状态。

## 性能证据的门槛

- 新缓存、位图、索引和状态要有显著、可重复的普通 MIDI 完整渲染收益，才值得增加维护负担。密集 MIDI、局部 micro 或扫描次数下降不能单独支撑上游化。
- 微小、无额外维护负担的正确性／开销修复单独判断；#1886 被接受，但不能把 Note On 局部提速写成整体渲染提速。
- 固定源码、工具链、SoundFont、精度、采样率与线程数；基线／候选交错配对，保留原始数据、无变化对照和不确定性。区分完整进程、加载、render-only 与 micro，不沿用另一版本或组合栈的收益。
- 涉及自动向量化等编译器行为时，交代受阻机制与方案取舍，优先提供可直接试验的最小 Compiler Explorer 示例和工具链／选项。汇编、向量化诊断与跨架构编译结果不冒充目标平台实测；不能因一种编译器已能优化，就假定其他编译器也一样。#1910 中维护者认可指针偏移，是因为仅缩小／提升索引类型能解决 GCC，却仍不能解决 MSVC；这不是普遍改用 unsigned 或宽整数的要求。
- PCM 逐位相同则说明覆盖范围；不同时量化最大误差、RMS 和原因。并行求和先测基线自身波动；IIR 数值精度必要时比较收敛的高精度参考，不仅比较旧输出。
- 实测中性、回退或机制不成立就停止。相位缓存未减少目标转换调用、unity-gain 分支普通 MIDI 回退等已拒绝实验，只有新证据才重启。

## 分支、正文与评审

1. 开发分支用 fix/dev-<topic>、perf/dev-<topic>、ci/dev-<topic>、refactor/dev-<topic>，topic 为简短英文 kebab-case，不加日期或临时版本后缀；保留原开发提交历史。先完成自查和必要测试，再从最新上游建立去掉 dev- 的对应分支（例如 fix/dev-sostenuto-cycle → fix/sostenuto-cycle），整理成一个完整 commit，不把 dev 历史或 todo 混入。初次投稿仅有明确审查分层需求时才保留多提交；已有 PR head 不擅自改写历史。按用户在 #1910 中的明确要求，评审修正新增普通提交并普通 push，不为维持单提交而 amend／rebase／force push；需要改写时另取授权。推送前核对相对上游的提交数与完整 diff。
2. 提交作者按用户约定使用 Yikai-Liao。Commit 标题用简短英文动词短语，直接说明行为变化，沿用上游风格，不强套 Conventional Commits；正文交代触发条件、根因、为何此修复足够及关键回归，不塞入整份审计／实验报告。PR 正文同样简短：场景与后果 → 根因和最小修复 → 实际验证及限制 → 关联 issue 与 AI 披露；详细数据只有帮助判断时才放图表或折叠段。
   自查必须覆盖生产逻辑、测试规模与职责、函数／变量命名、注释、commit 消息、仓库设施复用及完整 diff；修复旧 bug 的同时保护邻近合法行为。不要仅因代码少或测试通过就宣称已精简完成。
   MIDI controller 修复在 PR 标题和正文写明具体编号（例如 CC66），不只用踏板英文名，方便搜索和区分。同日提交相近问题时保持独立基线与最小 diff；投稿前验证双向试合并无冲突，并跑组合回归，避免给维护者增加处理冲突的负担。
3. 如实披露 AI 辅助，按实际工具和已知精确模型填写；历史常用句是 `AI-assisted with Codex`，不可冒称本次用了 Codex 或照抄历史模型名称。用户承担复核，不能把 AI 断言当验证。
4. 先回答维护者具体问题，说明已查到什么、改了什么和在哪个提交；必要时提供最小复现、输入资产、命令与预期／实际结果。区分对方的诊断实验、最终选择和实际修改要求，不把探索性替代方案一并落地。解释方案为何必要的技术结论按要求写回 PR 正文，不只留在评论或本地记录；保留推测语气与来源，不把编译器行为推断写成已证实根因。避免贴大段 AI 解释或持续重写迫使对方从头 review。接受方案不等于 APPROVED、CI 全绿或合并。
5. 维护者明确选择更可理解的行为后，不仅凭规范边角继续增加状态和特例。尊重其声明自做的工作、审核节奏和资源限制，不催审、不以漏洞披露施压发版。
6. 选题和本地验证不等于授权开 PR。根据用户本次授权推送 fork 或提交上游；每次只推进当前安排的问题，不凑数批量投稿。

## 维护这份 skill

稳定判断留在本文件；出处与 PR 索引留在 history.md；当前状态、选题和暂缓队列只维护 todo README。历史实验通过固定提交回查，不再追加会话流水。新反馈先判断是在修正规则还是一次例外，不将一次合并或一句 LGTM 升格为普遍偏好。
